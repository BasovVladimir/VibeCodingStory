## ⚠️ КРИТИЧНО: два продуктовых инварианта (это медданные)

1. **Все назначения — только со врачом.** Сервис НЕ ставит диагнозы, НЕ назначает и НЕ отменяет
   лечение, НЕ дозирует препараты. Роль сервиса — память, порядок в данных, динамика, подсказки
   по образу жизни (еда, спорт) и **список вопросов к врачу**. Любая аналитическая выдача по
   здоровью — со штампом «это не медицинский совет» и с явным «обсудить с врачом: …».
2. **Медданные не покидают периметр без явного решения PO.** `data/` — никогда в git. Внешним
   LLM-API медданные по умолчанию НЕ отправляются (открытый вопрос №3 в `docs/PRODUCT_PLAN.md`,
   решается PO отдельно и осознанно). Тесты — **только на синтетических данных**; реальные
   выгрузки PO в тесты и фикстуры не вшиваем никогда.

## Данные: инварианты

- **`data/raw/**` — личные сырые данные, в git не попадают никогда** (закрыто `.gitignore`,
  держим так).
- **Импорт идемпотентен:** повторный импорт того же файла не плодит дубли (Этап 1; до его
  реализации — не гнать импорт одного файла дважды).
- **Единый словарь метрик** (`ingest/metrics.py`): одна и та же метрика из разных источников
  сводится к одному каноническому имени — иначе динамика не сравнится.
- **Источник правды по документу — сам файл** в `data/raw/medical/`; в БД — извлечённый текст,
  структурированные findings и ссылка на файл.
- **PDF/документы распознаём конвейером из reports** (PyMuPDF + tesseract OCR): решение и
  граница реюза — `docs/adr/0001-pdf-конвейер-из-reports.md`.

## Код и тесты — коротко

**Правку кода без зелёного `make test` не сдаём** (unit + e2e). Тесты в сеть не ходят, фикстуры
строятся на боевых моделях SQLAlchemy, а не на выдуманной схеме. Код самодокументируемый:
docstring «зачем», inline на неочевидном, `AI:`-тег на новых граблях (без тега грабли не
сдаём — проверяется на приёмке), метка задачи (`# Э1.2`).
**Всё разворачиваем в Docker** (исключение — физически привязанное к маку; см. практику).
Подробности — `docs/practices/код-и-тесты.md`.

## Роли, эпики, кодер — коротко

- **PO — Владимир** (продукт, стратегия, приёмка; системный аналитик, код не пишет).
  **Архитекторы** — Claude Opus, Kimi K3, Qwen 3.8Max — равны и взаимозаменяемы: один и тот же
  процесс для всех троих. **Кодер** — **DeepSeek** (через CLI, автономный цикл), руки нового
  кода; работает в отдельной рабочей копии на ветках `feat/*`, в `main` не мержит.
  **GLM больше не кодер** — не привлекать.
- **Формат работы с PO — КОЛЛЕГИАЛЬНЫЙ:** выдача = рекомендация с обоснованием, не вердикт;
  решение совместное. Архитектура и план — до кода.
- **Эпик = бизнес-функционал** (нужны бэк + фронт + тесты — всё в ОДНОМ эпике, вертикально).
  **Наряд = документ на эпик.** ⛔ Граница документов: `docs/План и реализация.md` = ЭПИКИ,
  `docs/наряды/` = ЗАДАЧИ. Новую задачу в план НЕ заводим.
- **Декомпозицию делает архитектор** — не PO и не кодер. Режим запуска («под ключ» / «пауза
  после батча») задаёт PO строкой в шапке наряда.
- **Кодеру отдаём только механичное, с машинной проверкой, изолированное** (полный критерий —
  `docs/practices/Роли и воркфлоу.md` §5). Сдача — только зелёный гейт; красный гейт = возврат
  без разбора; два прохода архитектора максимум.
- **⛔ Максимум ОДИН субагент на задачу.**
- **Качество выше токенов и времени.** Токены экономим структурой работы, не срезая проверки.
- **⛔ ЕДИНИЦА ИЗМЕРЕНИЯ — ЛИМИТ АРХИТЕКТОРА, НЕ ДЕНЬГИ** (решение PO 11.08): у PO подписки,
  дефицитен недельный/месячный лимит — свой у Claude, Kimi, Qwen. **Кодер бесплатен по всем
  фронтам**, его круги стоят ноль, и разделение работы с ним нужно ровно для сбережения лимита.
  Расход ≈ **длина контекста × число запросов**, вывод — доли процента: экономим структурой
  сессии («фаза = сессия»), не урезая ответы и проверки. Приёмы и порог передачи —
  `docs/наряды/README.md` §10.

Полностью — `docs/practices/Роли и воркфлоу.md`; механика нарядов — `docs/наряды/README.md`.
